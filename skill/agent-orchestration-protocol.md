# 自適應多代理實作協議

以目標、驗收條件和可定位證據為主軸。主 agent 維持範圍、授權、所有權與最終驗收。

## 路由

只對程式實作啟用；說明、唯讀檢查或非開發請求不需啟用，除非使用者明確要求本協議。

- **Lightweight（預設）**：小型、範圍明確、低風險且可由少量檔案完成的工作，依 `brief → inspect → edit → validate → deliver` 執行，不建立完整階段儀式。
- **Strict**：跨模組或多檔案、契約／狀態變更、重要歧義、高風險副作用、可安全切分的多項工作，或使用者明確要求分階段時，依 `requirements → retrieval → design → implementation → verification → delivery` 設置必要 checkpoint。只展開會改變結果的欄位；非關鍵未知不應阻斷安全工作。

## 任務契約

開始時記錄最小必要資訊：

- 目標、範圍、驗收條件及每項所需證據。
- 硬性限制、可用授權與副作用邊界。
- 受影響的檔案／模組；有委派時指定唯一 owner。
- 會改變結果的未知、假設、風險與阻塞。

只有跨模組、狀態／契約變更或高風險工作，才補充資料結構、狀態轉移、介面與任務依賴。

## 能力導向委派

依可用能力路由（例如探索、文件研究、設計、實作、測試），不把固定角色名稱當成前置條件。

- 只有能力可用、任務範圍窄且輸入／輸出與驗收清楚時才委派。
- 沒有合適 subagent、委派失敗或 runtime 不支援時，由主 agent 直接完成；不得虛構角色或因缺少角色而停擺。
- handoff 至少包含 `scope/owner`、輸入／輸出、驗收與證據、假設、風險、狀態。避免大段原始碼，除非摘錄本身是必要證據。

## 所有權與排程

- 並行工作必須有不重疊的檔案／模組所有權，且彼此獨立、沒有共享契約或狀態；有依賴、共享檔案或共享契約時串行。
- 主 agent 負責整合與檢查。保留既有或並行中的修改，不回退其他 agent 的工作。

## 實作、測試與修復

依使用者需求、專案規範與可用能力選擇 TDD／test-first、整合測試、回歸測試或其他必要驗證；不得預設禁止測試工作。使用專案允許的命令並保留結果證據。

驗證失敗時，只針對具體錯誤執行範圍內的 focused repair，最多兩次；每次修復後重新驗證。兩次仍無法完成時標記 `BLOCKED`，說明錯誤、已嘗試內容與所需下一步。

## 授權與副作用

委派不會擴大授權。未獲明確授權，不得執行 commit、push、PR、對外寫入／傳訊、破壞性或高成本動作，或擴大任務範圍。缺少授權時可繼續安全、可逆且在範圍內的局部工作；受影響的驗收項目須列為阻塞。

## 狀態與交付

最終狀態使用以下值之一：

- `DONE`：所有必要驗收條件均有通過證據。
- `NO_OP`：檢查後確認不需變更，並交付檢查證據。
- `CANCELLED`：使用者取消工作或撤回必要授權。
- `BLOCKED`：缺少關鍵資訊／授權，或限定修復次數後仍無法安全完成。

交付時由主 agent 對每項驗收條件建立 `criteria → evidence` 對照，並回報：結果與狀態、變更檔案、驗證命令／結果、假設與限制／風險、必要的下一步。subagent 不得代替主 agent 做階段轉移或最終驗收決定。
